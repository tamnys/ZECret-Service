# Gate D source analysis

Checked 2026-09-25. Scope: upstream stable production source and release metadata, without cloud access, execution, artifact reproduction or deployment. This record does not approve a platform tuple or close a live gate.

## Decision

The default v0.5.11 runtime conflicts with the design's Gate D requirement to persist only public node state and never load executable/configuration state from persistent writable mounts. An image digest in Compose does not resolve the persisted runtime-state path. Gate D therefore blocks using that default configuration for the proposed privacy claim. This is a configuration incompatibility; it is not proof that every Phala configuration fails or that the provider can currently decrypt request memory.

## What the stock boot path does

The [preparation script](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/dstack-prepare.sh#L262) calls disk setup, then creates and recursively bind-mounts persistent directories onto `/var/lib/docker`, `/var/lib/containerd` and `/var/lib/sysbox` at lines 264–273. This is runtime state, not merely the Zebra database. Docker documents [image and writable container layers](https://docs.docker.com/engine/storage/drivers/) in its data directory.

The [app launcher](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/app-compose.sh#L23) executes `docker compose up --remove-orphans -d --build`, then prunes unused images/volumes. It does not rebuild an empty runtime root before launch. Docker's [Compose semantics](https://docs.docker.com/reference/cli/docker/compose/up/) permit existing containers to remain when configuration/image is unchanged. The preceding [orphan cleanup](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/dstack-util/src/docker_compose.rs#L147) examines container configuration to remove orphans; it does not authenticate executable bytes. The reviewed dstack boot path establishes no per-boot authentication of reused runtime layers or snapshots against independently approved content. This is not an exhaustive audit of every Docker/containerd version.

## Rootfs integrity is a different boundary

The OS [base recipe](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/meta-dstack/recipes-core/images/dstack-rootfs-base.inc#L80) builds a read-only squashfs with dm-verity. [Image packaging](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/mkimage.sh#L80) places the root hash and data size in the kernel command line; the [initramfs](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/meta-dstack/recipes-core/images/dstack-initscript/init#L18) opens that verity device before mounting rootfs. Correctly verifying the measured boot configuration is essential to trusting that root hash. This rootfs path does not authenticate the separate writable runtime directories.

The [disk setup](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/dstack-util/src/system_setup.rs#L156) defaults to encrypted ZFS; kernel options can alter this. Existing data is mounted at lines 1159–1187. The LUKS validator requires `aes-xts-plain64` and rejects an integrity field at lines 1735–1762. These checks do not establish executable authenticity or rollback protection.

## KMS control and the limit of this finding

The [KMS service](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/kms/src/main_service.rs#L247) checks an attested boot against configured authorization, then derives the disk key from its root key and `(app_id, instance_id, "app-disk-crypt-key")` at lines 295–337. Compose hash and OS image hash are not inputs to that derivation. Thus, conditional on authorization permitting a different workload with the same app/instance identities under the same KMS root, it receives the same disk key. This is a source-derived conditional result, not evidence that the selected cloud KMS permits that boot. The [authorization implementation](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/kms/src/main_service/upgrade_authority.rs#L142) delegates production decisions to its configured webhook. The actual deployment's KMS identity, root, authorization policy and upgrade authority remain unknown.

Persisted executable state therefore needs its own solution even when the native client independently rejects altered boot measurements. This review does not establish a provider plaintext attack, and disk encryption alone does not satisfy the project's stronger persistence rule.

## Can application configuration fix the order?

The [whole app-compose file is hashed into the application event sequence](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/dstack-util/src/system_setup.rs#L1298). Its `init_script` is [sourced after persistent mounts but before preparation completes](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/dstack-prepare.sh#L282). Both [Docker](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/docker.service.d/dstack-prepare.conf) and [containerd](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/containerd.service.d/dstack-prepare.conf) are ordered after preparation. This provides a candidate place for a measured, immutable startup configuration to establish fresh memory-backed runtime state before normal startup. No such configuration was authored or tested here.

An ordinary service-level Compose `tmpfs`/`read_only` does not replace the host runtime roots. `pre_launch_script` runs in [app-compose.service after Docker](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/app-compose.service#L3), so it is not an adequate pre-reuse boundary. Failure handling also needs proof: the runtime drop-ins use `Wants`/`After`, while [preparation](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/basefiles/dstack-prepare.service) requests reboot on failure. [systemd documents `Wants` as a weak dependency](https://github.com/systemd/systemd/blob/v257/man/systemd.unit.xml#L641); ordering alone must not be treated as proof that a failed setup prevents runtime startup.

## Gate C controls and remaining decision

The production recipe [enables `nologin`](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/meta-dstack/recipes-core/images/dstack-rootfs-prod.inc), whose [implementation](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/meta-dstack/recipes-core/images/dstack-rootfs-base.inc#L125) removes getty/login components and the debug-shell unit. The [development recipe](https://github.com/Dstack-TEE/meta-dstack/blob/ce04e924e17e3cb9d38d258338cbe71e8c08d575/meta-dstack/recipes-core/images/dstack-rootfs-dev.inc) adds SSH and debugging packages. The inspected [host-facing GuestApi definition](https://github.com/Dstack-TEE/dstack/blob/40eaf35e6b3f112998d01569f2a26110baab123b/guest-api/proto/guest_api.proto#L133) has no exec operation; that scoped observation is not proof of absence across a deployed guest. Approved startup scripts must be fixed in independent release policy, and actual production artifacts, interfaces and configuration still need verification.

Before choosing a cloud deployment, the operator needs an available, supported production image/KMS tuple and a decision on runtime architecture: an audited early ephemeral-runtime configuration or a separately built measured OS that enforces the same boundary. Acceptance then requires proving that normal boot, restart and setup failure cannot consume persisted executable/configuration state, and that the resulting runtime plus testnet node fits the quoted RAM without persistent swap. Those are follow-on gate proofs, not M0 implementation or deployment authorization. Gates A–E remain unresolved; simulation remains usable.
