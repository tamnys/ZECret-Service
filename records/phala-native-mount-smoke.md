# Native amd64 Phala preview mount smoke — 2026-09-30

The public GitHub x86_64 [workflow run 36691556365](https://github.com/tamnys/ZECret-service/actions/runs/36691556365) completed successfully at source commit `e997f420c652ff5bec4fbe641bbc5e6b3d97d8f3`. It rebuilt the pinned local image without publishing it, then ran `deploy/phala/check_native_mounts.py` against that image. No Phala API call, CVM, image upload, or account spend occurred.

The test created a local Docker named tmpfs volume with the launch document's `uid=0,gid=0,mode=1775` options and a separate local public-state volume. With networking disabled, a read-only root filesystem, all capabilities dropped, and `no-new-privileges`, the quote identity (`10002:0`) observed `/run` as tmpfs and a synthetic bind-mounted Unix socket at `/run/dstack.sock`. While that quote container remained running, the app identity (`10001:0`) read and updated a group-writable marker in the same tmpfs, found no usable dstack socket in its own mount namespace, observed a non-tmpfs public-state volume owned by UID 10001, and wrote to that state volume and `/run`. The script removed its test-owned container and volumes; the runner step exited successfully.

The first, sequential version of this probe [failed](https://github.com/tamnys/ZECret-service/actions/runs/36690979577) because no container held the tmpfs volume between the two runs. The final probe keeps the quote container alive, as the Compose design intends with `depends_on: service_healthy`. This finding makes concurrent lifetime a requirement for the shared memory volume. It does not prove Phala's actual Compose mount behavior, quote-socket access, service restart handling, snapshot import, Zebra/wrapper operation, full guest resource fit, or a TDX attestation. Those remain hardware or complete-service tests. The stock Phala guest still does not satisfy genuine private-mode requirements.
