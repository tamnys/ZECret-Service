TWO SEPARATE CHECKS

Privacy has more than one boundary.

01 / NETWORK

Tor hides the direct route.

The native client uses Tor for private sessions. It does not anonymize this browser visit or guarantee resistance to traffic analysis.

02 / EXECUTION

Attestation checks the workload.

The client checks a trusted release, hardware evidence, freshness, and the live TLS connection before sending a query. A website badge cannot do that check for you.

DEVELOPER QUICKSTART

Start with the native client.

Build from source on Linux with the pinned Rust 1.94.1 toolchain and committed Cargo.lock. The current CLI offers local synthetic examples and a bundled loopback dashboard.

There is no approved release download or checksum to link yet. Source code alone does not approve a private deployment.

Read the repository setup guide →
LOCAL · SYNTHETICzrpc
cargo build --locked -p zrpc-cli
./target/debug/zrpc doctor
./target/debug/zrpc query --simulate --method getblockcount
./target/debug/zrpc query --simulate --scenario wrong-key
./target/debug/zrpc demo

Private commands require an approved release and live verification; this build does not package one. The dashboard opens locally through the native CLI.

Supported read-only methods

  • getblockchaininfo
  • getblockcount
  • getblockhash
  • getblockheader
  • getrawtransaction

Wallet methods, transaction submission, batches, and arbitrary upstream URLs are rejected. Parameterized requests use the native client’s typed request format; the simple --method example above uses a method with no parameters.

OPTIONAL PAYMENT CONCEPT

Prepaid credits, held locally.

The proposed flow is simple: buy a batch, keep blinded one-use tickets in the native client’s private store, and spend one ticket when a request is admitted. That avoids an on-chain transaction for every query.

For this experiment, settlement would be a private operator file exchange, illustrated only with fixtures here. Issuance and redemption are not implemented, and no real or testnet ZEC payment is accepted. A ticket can be consumed even if the node fails or the response is lost; the client must not automatically spend a replacement.
